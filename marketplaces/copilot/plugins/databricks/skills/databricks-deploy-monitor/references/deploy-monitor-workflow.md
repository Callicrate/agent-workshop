# Deploy-Monitor Workflow

Codify the delivery unit as a single increment only when live Databricks execution is in scope: local tests, bundle validation, deployment, run monitoring, output contract verification, and live job-setting verification.

This prevents treating deployment checks as optional follow-up work without turning review-only or config-only tasks into accidental live operations. Classify live actions with [operation-classes.md](operation-classes.md) first.

## Completion Definition

- Use this full loop when the user explicitly asks to deploy, run, watch, monitor, verify a live job, or fix a live Databricks failure.
- For production activation, destructive changes, traffic shifts, schedule changes, reruns, repairs, cancels, alias moves, or paid/long-running operations not already authorized, stop at a ready-to-run plan or manifest.
- `done` means the validation/deploy/run loop reached terminal success or a concrete blocker.
- A code patch, generated bundle, or started run is not complete until the relevant local check, bundle validation, deployment, and run monitoring steps have passed or a blocker has been identified.
- If the project was generated by an agent, validate the emitted bundle shape before deployment. Generated DABs fail often at the bundle boundary even when source files look plausible.

## 0. Local Tests (Fast Feedback)

- Run unit tests and any fast integration tests locally.
- Fix red tests before packaging.

## 1. Validate the Bundle (Preflight)

Before validation, prove the CLI profile and workspace target unless the current session already did:

```bash
databricks current-user me --profile <profile> -o json
```

The profile, workspace host, bundle target, and user/service principal must match the intended deployment context.

If a static bundle validator is present, run it before the Databricks CLI validation:

```bash
python scripts/validate_bundle.py .
```

```bash
databricks bundle validate --profile <profile> --target <target>
```

Use the project-approved profile/target command shape when the bundle encodes authentication or target defaults. Record resolved host, principal, and target whenever a flag is intentionally omitted.

- Abort on validation errors. Do not deploy with a red validate.
- For generated bundles, fix validation errors in the owned bundle config or owned template so the next validation run stays clean.

## 2. Deploy and Start a Monitored Run

Confirm that deployment and execution trigger are authorized by the user request or existing task contract before running these commands.

```bash
databricks bundle deploy --profile <profile> --target <target>
databricks bundle run <resource-key> --profile <profile> --target <target> --no-wait
```

Do not run these live commands unless deployment and execution trigger authority are in scope.

- Capture the exact positive `run_id` from this launch before any monitor call. Keep the explicit `<profile>` and the preflight-verified workspace host with that identity in the run ledger; use the same profile and host for every subsequent monitor and output read.
- Run the launch from the target bundle/project root containing `databricks.yml`, never from the installed skill package. The documented `bundle run` terminal surface presents a `Run URL`. Capture the output of the exact launch command to an explicit temporary or target-project ledger path, then extract only that direct URL. Never write a capture into the skill package. Do not add `-o json` or assume an undocumented `bundle run` JSON schema.

On PowerShell, preserve the native launch exit code before writing output or invoking the extractor. This pattern does not run the extractor after a failed launch:

```powershell
$launchCapture = Join-Path ([System.IO.Path]::GetTempPath()) "dab-launch-$([guid]::NewGuid().ToString('N')).txt"
try {
    $launchLines = & databricks bundle run <resource-key> --profile <profile> --target <target> --no-wait 2>&1
    $launchExitCode = $LASTEXITCODE
    $launchText = [string]::Join([Environment]::NewLine, @($launchLines | ForEach-Object { "$_" }))
    [System.IO.File]::WriteAllText($launchCapture, $launchText, [System.Text.UTF8Encoding]::new($false))
    if ($launchExitCode -ne 0) {
        Write-Error "DAB launch failed; direct Run URL extraction was not attempted."
        exit $launchExitCode
    }
    $extractor = '<skill-root>/scripts/extract_launch_run_id.py'
    & python $extractor --workspace-host <verified-workspace-host> --launch-output-file $launchCapture
    $extractorExitCode = $LASTEXITCODE
    if ($extractorExitCode -ne 0) {
        Write-Error "Monitoring identity blocker; do not start monitoring."
        exit $extractorExitCode
    }
} finally {
    Remove-Item -LiteralPath $launchCapture -ErrorAction SilentlyContinue
}
```

- The extractor accepts exactly one `Run URL:` line, normalizes and matches its HTTPS host to `<verified-workspace-host>`, and returns its positive signed-64-bit `run_id`. The current CLI launch URL must be exactly either legacy `https://<host>/?o=<positive-workspace-id>#job/<positive-job-id>/run/<positive-run-id>` (an empty path is also accepted) or modern `https://<host>/jobs/<job-id>/runs/<run-id>?o=<positive-workspace-id>`. It rejects extra or duplicate query fields, userinfo, ports, fragments on the modern form, and alternate paths. The already verified canonical UI form without a query remains accepted only as `https://<host>/jobs/<job-id>/runs/<run-id>`.
- A previously recorded positive `run_id` is usable only when its launch response or Run URL was verified in the same explicit profile and workspace host. Record the resource key, job ID, run ID, Run URL, profile, host, and capture time together.
- If resuming an existing session, reuse the known `run_id` and skip the start step.
- Never recover a launch identity with `databricks jobs list-runs --limit 1`, a newest-row query, timestamps, or a matching job ID. A concurrent launch can make that query identify run B while this launch created run A.
- If the direct launch identity is absent, malformed, host-mismatched, or ambiguous, stop with the relevant `monitoring_identity_*` blocker from the extractor. Do not monitor, choose a candidate, or start a recovery query. Repeat the launch only when a new execution trigger is authorized; otherwise report the concrete monitoring-identity blocker.

## 3. Poll Until Terminal

From the `databricks-deploy-monitor` skill package root, use the public helper:

```bash
bash scripts/check_run_status.sh <run_id> <profile>
```

- Pass a nonempty explicit named profile, including `DEFAULT` only when it is deliberately named. The helper never substitutes a default profile.
- On Windows, use a real `databricks.exe`, not a `.cmd` or `.bat` wrapper. The helper rejects wrapper resolution to prevent opaque pagination tokens from entering `cmd.exe` parsing.
- Poll every 30-90 seconds.
- Read `status.state` first. Under the current Jobs API, terminal success is exactly `status.state=TERMINATED` with `status.termination_details.code=SUCCESS`.
- The deprecated `state` object is a fallback only when `status` is absent. If both disagree, report the conflict and retain the current status result.
- Continue through `BLOCKED`, `PENDING`, `QUEUED`, `RUNNING`, `TERMINATING`, and `WAITING`.
- A nonzero helper exit means the snapshot is incomplete, malformed, unavailable, or unsafe to interpret. Do not declare success from it.
- Do not stop after reporting that a run has started or is still running. That is an intermediate state, not a result.
- If the user says to watch the run, keep the monitoring loop active in this session instead of treating it as background work.

The helper uses `databricks jobs get-run <run_id> --profile <profile> --include-history -o json` and follows `--page-token` values only while its bounded pagination contract remains coherent. Databricks documents the current `status` and `termination_details` fields in the [Jobs Get Run API reference](https://docs.databricks.com/api/jobs/v2/get-run), and documents `get-run` array pagination plus `--include-history` in the [Databricks CLI Jobs reference](https://docs.databricks.com/aws/en/dev-tools/cli/reference/jobs-commands).

## 4. Interpret Terminal State

| Field | Value | Action |
|-------|-------|--------|
| `status` | `TERMINATED` | Inspect `termination` |
| `termination` | `SUCCESS` | Run output contract verification |
| `termination` | a known non-`SUCCESS` code | Diagnose or report the terminal failure without inventing a retry |
| `source` | `legacy_state` | Treat as compatibility evidence and plan to use current status on the next response |
| `mixed_state_conflict` | `true` | Report the conflict; never let deprecated state override the current status result |
| `tasks_complete` | `false` | Treat the monitor read as incomplete and retry the read safely; do not declare success |

`result_state` can be empty before the run reaches a terminal lifecycle state.

## 5. Pull The Right Output

```bash
databricks jobs get-run-output <task_run_id> --profile <profile> -o json
```

- Single-task job: use the parent `run_id`.
- Multi-task job: inspect the helper's `failed_task_runs`, which select the current root-task attempt using repair history and attempt number. Then call `get-run-output` with that failed task's `run_id`.
- For a ForEach parent run, inspect `failed_iteration_runs` separately. Do not confuse a historical failed iteration or repaired root-task attempt with the current root-task failure.
- Fix the first failed task, not downstream cancellations caused by that failure.

## 6. Apply The Loop

1. Pull the failing task output and error message.
2. Read the referenced source or bundle files.
3. Match the first actionable error, not repeated downstream symptoms.
4. Apply the smallest fix that addresses that first failure.
5. Validate locally if the check is cheap and reliable.
6. Redeploy, rerun, and return to polling.

### Stalls and stale output

- If a bare Python command appears hung, inspect process state and recent log writes before assuming success or failure.
- If a build log stops changing, check whether the process is still alive, killed, waiting on input, or writing elsewhere.
- Treat process kills, stale logs, and no-output runs as loop signals: diagnose, patch the command/config if needed, and continue to the next validation step.

### Rerun boundaries

- If the user asked for a full deploy-monitor cycle, rerun after each fix until success or escalation.
- If the user explicitly says "do not rerun", "do not run it", "fix only", "pause", or "I have more work queued", stop before triggering a new run and report exactly what was fixed.
- If a run was canceled externally, inspect context before restarting. Ask only if cancellation may have been intentional.
- If repair is explicitly authorized and can resume only failed tasks, prefer repair over rerunning successful expensive tasks. Without authorization, prepare the repair command or payload but do not trigger it.

This is a hard gate. Under a no-rerun instruction, only local validation, static validation, and read-only Databricks checks are allowed.

Production activation, schedule unpause, traffic movement, model alias movement, active run cancel/repair, and destructive reset/delete operations require explicit approval plus resource identity proof.

## 7. Output Contract Verification (Required When Outputs Exist)

After terminal success, verify declared outputs before reporting the run as verified. Use [output-contract-verification.md](output-contract-verification.md) for SQL and sampling patterns.

1. identify the main output table, audit tables, registered models, aliases, or scored data the job owns
2. run contract SQL for the requested date or source window
3. compare row counts and key distributions to expected values
4. check null and unscorable behavior when source values can be missing
5. for SCD2 outputs, check `valid_from`, `valid_to`, `is_current`, and overlap rules
6. sample reasonable data from the main output table before declaring the run verified

Terminal `SUCCESS` is not enough when a job writes data or mutates registry state.

## 8. Live Job-Setting Verification (Required)

### Production-Activation Gate

Before unpausing a schedule, moving production traffic, moving a production model alias, enabling a trigger, or removing a dry-run flag for production, confirm all three gates:

1. Service-principal `run_as` is configured (no personal users in prod).
2. Analyst/stakeholder review criteria are documented and met (row counts, distributions, null checks, business sanity).
3. Explicit production approval is recorded (PR comment, Slack, or ticket) and referenced in the commit/PR.

Do not repair, cancel, delete/reset, or restart production resources unless that exact action is explicitly requested and the resource identity has been proven from the API.


After a successful run, verify critical job settings in the workspace to catch drift:

```bash
databricks jobs get <job_id> --profile <profile> -o json
```

Check at minimum:

- cluster policy and node type match bundle expectations
- libraries match expected versions
- schedule is enabled/disabled as intended
- runtime version and spark_conf align with bundle
- permissions reflect least-privilege intent

If any mismatch, file a follow-up fix immediately (same delivery unit).

## 9. Notebook-To-Job Readiness

Before deploying code converted from notebooks or interactive experiments, check job entrypoint readiness:

- no hidden kernel state or dependency on prior notebook cell execution
- deterministic imports at module or entrypoint startup
- widgets mapped to bundle parameters or `argparse` arguments
- required parameters validated before Spark work starts
- no inline DDL outside owned deployment SQL files
- small dry run or static command shape check before deployment when practical

## 10. Escalation Rule

Escalate when any of these are true:

- permissions, expired credentials, or workspace access block the run
- business logic is ambiguous and code changes would guess at intent
- the platform still fails after one clean retry with no code change
- the same error returns after 3 distinct fix attempts
- the user forbids reruns and verification requires another live run
